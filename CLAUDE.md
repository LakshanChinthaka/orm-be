# CLAUDE.md

NestJS 12 + MikroORM 7 (PostgreSQL) backend for a multi-tenant business platform. ESM project (`"type": "module"`), pnpm, Vitest, oxlint, Prettier.

## Commands

```bash
pnpm dev                    # watch mode
pnpm build                  # nest build -> dist/
pnpm lint                   # oxlint --type-aware
pnpm format                 # prettier --write
pnpm test / pnpm test:e2e   # vitest

pnpm db:migration:create    # after `pnpm build` (CLI reads dist config first)
pnpm db:migration:up
pnpm db:migration:down
pnpm db:seed:permissions | db:seed:countries | db:seed:addresses
```

Type-check without building: `npx tsc --noEmit -p .`

### Schema change workflow
1. Add/modify the entity in `src/modules/<module>/entities/`.
2. **Register new entities** in the `entities` array in `src/core/db/mikro-orm.config.ts` — an unregistered entity fails at runtime.
3. `pnpm build` → `pnpm db:migration:create`.
4. Review the generated file in `src/migrations/` before `pnpm db:migration:up`. Never edit an applied migration; create a new one.

## Folder structure

```
src/
├── main.ts                     # bootstrap: global ValidationPipe, swagger, cors, cookies
├── app.module.ts               # root module: config, logger, MikroORM, feature modules
├── core/                       # infrastructure wiring (no business logic)
│   ├── db/mikro-orm.config.ts  # entity registry + migration config
│   ├── swagger/
│   └── cors/
├── common/                     # cross-cutting, module-agnostic
│   ├── decorators/             # @Permissions(...)
│   ├── guards/                 # JwtAuthGuard, PermissionsGuard
│   ├── filter/                 # exception filters
│   └── logger/
├── modules/<module>/           # one folder per bounded context
│   ├── <module>.module.ts
│   ├── <module>.service.ts
│   ├── admin-<module>.controller.ts     # routes under  admin/<module>
│   ├── customer-<module>.controller.ts  # routes under  app/<module>
│   ├── entities/<name>.entity.ts
│   ├── config/                 # module-specific config (optional)
│   └── dtos/
│       ├── admin/              # admin-only request/response DTOs
│       ├── customer/           # customer-only DTOs
│       ├── public/             # unauthenticated DTOs
│       ├── common/             # shared/nested DTOs used by both portals
│       └── index.ts            # barrel — re-export every DTO
├── migrations/                 # generated by MikroORM
└── seeders/                    # standalone seed scripts (run from dist/)
```

Keep this structure. New features go into an existing module if they belong to that bounded context; otherwise create a new module (`npx nest g module|controller|service modules/<name> --no-spec`) and add it to `app.module.ts`.


## Conventions

### Imports
- ESM: relative imports **must** end in `.js` (`'./business.service.js'`), even for `.ts` sources.
- Import DTOs from the module's `dtos/index.js` barrel; import entities directly from their file.

### Naming
- Files: kebab-case. `<resource>-<action>-<type>.dto.ts`, e.g. `business-location-update.dto.ts`, `industry-type-filter-query.dto.ts`.
- DTO classes: `<Resource><Action>RequestDto` / `...ResponseDto` / `...FilterQueryDto`. Admin-only variants are prefixed `Admin...`.
- DB: snake_case tables and columns; TS properties camelCase mapped with `.fieldName()`.

### Entities (MikroORM `defineEntity`)
```ts
const fooSchema = defineEntity({
  name: 'Foo',
  tableName: 'foo',
  properties: {
    id: p.uuid().primary().fieldName('foo_id').defaultRaw('gen_random_uuid()'),
    barId: () => p.manyToOne(Bar).mapToPk().joinColumn('bar_id').deleteRule('no action'),
    isActive: p.boolean().default(true).fieldName('is_active'),
    createdAt: p.datetime().defaultRaw('now()').fieldName('created_at'),
    updatedAt: p.datetime().defaultRaw('now()').fieldName('updated_at'),
    deletedAt: p.datetime().nullable().fieldName('deleted_at'),
  },
});
export class Foo extends fooSchema.class {}
fooSchema.setClass(Foo);
```
- PK: UUID named `<table>_id`, generated by the DB.
- Relations: lazy `() =>` + `.mapToPk()` so properties hold raw IDs (`businessId: string`). Optional one-to-one: `.oneToOne(X).owner().nullable().mapToPk()`.
- `.mapToPk()` relations can't be filtered by nested fields (`{ subscriptionId: { userId } }` won't type-check) — query the related entity first.
- Soft delete via `deletedAt`; always filter `deletedAt: null` when reading.
- `updatedAt` has no on-update hook — set `updatedAt: new Date()` in update methods.
- **IDs are generated by the DB**, so an entity's `id` is undefined until `em.flush()`. Flush before using a new entity's id as a foreign key.

### DTOs
- Every field has `class-validator` decorators and `@ApiProperty({ example, required })`.
- Global `ValidationPipe` runs with `whitelist`, `forbidNonWhitelisted`, `transform`.
- Update DTOs: `PartialType(...)` / `OmitType(...)` from `@nestjs/swagger`.
- Nested objects: `@ValidateNested()` + `@Type(() => X)`.
- Target is ES2023, so **unsent DTO fields are present as `undefined`**. Strip them before `em.assign` (see `definedOnly` in `business.service.ts`) or partial updates will null out columns.

### Services
- Inject `EntityManager` and `PinoLogger` (`this.logger.setContext(X.name)` in the constructor).
- Multi-step writes go in `this.em.transactional(async (em) => ...)` and use the `em` passed in, not `this.em`.
- Logic that must join a caller's transaction gets a `...WithEm(em, ...)` variant (e.g. `createBusinessWithEm` used during registration). Public method = transaction wrapper; `WithEm` method = the logic.
- Validate referenced IDs exist → `NotFoundException`. Map `UniqueConstraintViolationException` → `ConflictException`. Bad input combos → `BadRequestException`. Never leak raw DB errors.
- Log successful mutations with the entity id.
- Generate display IDs with `generateDisplayId(prefix)` (`BUS-`, `LOC-`, ...).

### Controllers
- Thin: parse input, call one service method, return. No ORM access, no business rules.
- Admin and customer get **separate controllers** (`admin/<module>`, `app/<module>`), sharing one service.
- Use `ParseUUIDPipe` for UUID params. Add `@ApiTags('Admin Portal - X' | 'Customer Portal - X')` and `@ApiBearerAuth()` on protected routes.

## Auth & ownership rules

- `JwtAuthGuard` verifies the bearer token and sets `req.user = { sub, userType, userRoleId, businessId }` (`AuthUserPayload`). `userType` is `PLATFORM` (owner/operator, `AppUser`) or `STAFF` (`businessId` set in the token).
- `PermissionsGuard` + `@Permissions('resource:action')` enforce role permissions. Staff = role permissions ± `staff_has_permission` overrides. `super_admin` bypasses everything.
- New permission names go in `seeders/permission.seed.ts`.

### Admin = super admin
- "Admin" in this codebase means the **platform super admin**: a `PLATFORM` user whose role has `roleSlug === 'super_admin'`. There is no separate admin user table or admin token; admin and customer share one sign-in, so a valid token alone proves nothing.
- Every `admin/*` route must be guarded with `@UseGuards(JwtAuthGuard, SuperAdminGuard)` (`common/guards/super-admin.guard.ts`). `JwtAuthGuard` is usually applied at controller level and `SuperAdminGuard` per route.
- Super admins **moderate**, they don't edit tenant data. For business-owned records (business, business location, ...) the admin API only changes status — `PATCH admin/<resource>/.../status` with `StatusUpdateRequestDto { isActive }`. Content fields (name, contact, address, type, ...) are edited only by the owning customer through `app/*` routes.
- Super admins manage platform-wide reference data in full (industry types, location types, subscription plans, countries, ...).
- Business-owned admin endpoints today:

  | Route | Body |
  |---|---|
  | `PATCH admin/business/:businessId/status` | `{ isActive }` |
  | `PATCH admin/business/:businessId/location/:locationId/status` | `{ isActive }` |
  | `POST admin/business/:businessId/location` | `BusinessLocationCreateRequestDto` |
  | `GET admin/business`, `GET admin/business/:businessId` | `BusinessFilterQueryDto` (paginated) |
  | `GET admin/business/:businessId/location[/:locationId]` | — (locations include `address`) |

- Reference data is listed in full to admins and filtered to `isActive: true` for customers (e.g. `GET admin/business/location-type` vs `GET app/business/location-type`, `GET admin/address/country` vs `GET app/address/country`).
- In controllers, declare static routes (`location-type`, `industry-type`) before `:param` routes.
- Display IDs (`BUS-123456`, `LOC-123456`) are created with `generateUniqueDisplayId`, which checks for clashes before insert; never call `generateDisplayId` directly for a new row.

### Customer (tenant) routes
- **Customer routes must derive tenant scope from the token, never from the request.** Resolve the business with `resolveUserBusinessId(em, user)` and scope every child query by it (`{ id: locationId, businessId }`) so a foreign ID returns 404.
- Reach child records (e.g. an address) through their owning record, not by an ID the client supplies.

## SOLID, applied here

- **Single responsibility** — controllers do HTTP, services do business logic, entities describe the schema, guards do authorization, DTOs do validation. A service owns its module's entities; to change another module's data, call that module's service (export it from its module) instead of writing its tables directly.
- **Open/closed** — extend through new DTO variants (`BusinessLocationUpdateRequestDto` = `PartialType(OmitType(...Create...))`), new guards (`SuperAdminGuard`)/decorators, and new `WithEm` methods rather than adding `if (isAdmin)` branches to shared logic.
- **Liskov substitution** — a subclassed DTO must still be valid wherever its base is accepted: add optional fields, never loosen or contradict base validation.
- **Interface segregation** — keep DTOs per use case and per portal; don't reuse one big DTO for create/update/admin/customer. Keep typed payloads small (`AuthUserPayload`, `CreateBusinessInput`).
- **Dependency inversion** — depend on Nest-injected abstractions (`EntityManager`, services, `ConfigService`), not on concrete instantiation or `process.env` inside business code. Config is read in `core/` or via `ConfigService`.

General: keep changes minimal and consistent with neighbouring code, no dead code, no `console.log` (use the logger), comment only non-obvious *why*.
